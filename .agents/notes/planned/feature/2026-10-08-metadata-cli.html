让 agent 通过 CLI 和网页管理模组元数据

给现有的 Metadata CLI 增加一套新功能：创建模组目录、导入真实清单登记新版本、修改战网界面的按钮与背景样式、编写 Markdown 模组介绍、在本地网页里实时预览、以及创建 GitHub PR；同时编写配套的 agent skill，指导 AI 代理按顺序调用这些命令。

这些功能主要给 Modder 跑的 agent 使用，Modder 本人也可以手动使用。agent 运行 CLI 命令来读写文件并校验格式，用户也可以打开本地网页在界面上修改样式并查看预览。命令行和网页走同一套 C# 代码修改 XML 源文件，不写两套逻辑。Modder 如果不用 agent，也能在终端敲命令直接启动网页。

本次要做与明确不做的事情

  • 只改 Metadata 仓库，不改 Desktop 客户端。这一轮只写计划并提交到分支；后面编写代码时也只在 Metadata 仓库实现，不把修改 Desktop 代码当成前置条件。架构上先做好 Metadata，Desktop 客户端后续再独立接入。
  • 内置本地 Web 可视化页面。agent 是主要入口，同时工具在本地运行 Web 界面，不只是输出截图或在浏览器打开静态 XML；页面支持填写表单修改配置、编写 Markdown 介绍、挑选本地图片、查看实时渲染、比对改动差异并保存回文件。
  • 模组介绍用 Markdown 编写且不借用新闻。介绍属于模组自己的独立说明，不借用新闻的 Post.Descriptions 或 Posts 节点；Desktop 客户端后续单独增加渲染 Markdown 介绍的代码。
  • 更新模组只负责导入真实清单并登记版本号。更新时导入真实 Manifest 而不负责生成或上传，不计算安装文件的哈希值，不打包 zip，不上传文件到服务器，也不替代原本的 Updater 程序。
  • 新闻与 DLL 注入相关功能彻底排除。完全不新增新闻管理功能，也不新增 DLL 注入配置；文件里现有的 Posts、Dependencies 以及其他未编辑节点全部原样保留，工具不提供新闻编辑页面、命令或注入选项。
  • 提交 PR 之前必须展示改动差异并取得明确授权。向 GitHub 创建 PR 前必须向用户展示改动文件和差异文本，获得明确授权后才发起，不自动点击合并，不绕过人工审核；当前这一轮只推送计划分支，不自动创建计划 PR。

建议为介绍字段制定的格式规则

在 Mod 标签下新增可选的 Introductions，位置固定在 DisplayName 之后、Style 之前；容器标签一旦出现就必须包含至少一项。Introduction@Language 必须填写完整的语言标签，文本引用已登记的 Markdown 短 ID。介绍只属于模组自己，不从 Base 继承，也不给 Application 增加介绍功能。

<Metadata>
  <Markdown ID="intro-zh" Source="introductions/zh-CN.md" />
  <Markdown ID="intro-en" Source="introductions/en-US.md" />
  <Mod ID="ExampleMod">
    <DisplayName Language="zh-CN">示例模组</DisplayName>
    <DisplayName Language="en-US">Example Mod</DisplayName>
    <Introductions>
      <Introduction Language="zh-CN">intro-zh</Introduction>
      <Introduction Language="en-US">intro-en</Introduction>
    </Introductions>
    <Posts />
  </Mod>
</Metadata>

上面展示介绍字段最精简的 XML 格式示意，不是完整可安装的模组配置；里面省略了 Manifest 清单。

  • 同步更新源 XML 与发布 XML 的校验文件（XSD），并把介绍加入 IsTextReference 列表。在 ValidateHard 中新增专门放 Markdown 登记的 markdownIds 索引来校验 Introduction，不能使用混合 Image、Markdown 和 Manifest 的老索引 idIndex。遇到语言或引用为空、引用的 ID 不存在、或者误用了 Image 与 Manifest 类型时，校验必须报错失败。
  • XSD 负责约束节点层级与“出现容器则至少包含一项”；构建期大小写不敏感的语言查重在 ValidateHard 里实现，不能只依赖区分大小写的 xs:unique。将 Introductions 明确加入 MetadataInheritance.ModChildOrder 的 DisplayName 与 Style 之间，并且合并时保证只取当前 Mod 自己的介绍；否则继承合并时会把节点插入到错误位置导致校验失败。
  • 这些介绍规则后续要在模板文件、README.md 以及作为 AI 贡献者入口的 AGENTS.md 里同步写明；这些属于后续写代码时要做的事，当前这一轮不修改这些文件。
  • 协议版本继续沿用 SchemaVersion=1.0 的现行规定，明确旧客户端忽略介绍标签不等于已经支持介绍。C# 数据读取库提供按模组读取介绍列表与按语言精确查询的接口；网页预览时优先精确匹配，未命中则取 XML 中的第一项，并在界面上注明当前显示的是哪种语言。Desktop 客户端后续接入时也要严格遵守这个匹配逻辑。
  • 如果模组没有写介绍，源 XML 里就根本不写该节点；工具不替用户机器翻译英文，也不从正文里自动截取片段拼凑简介。仓库里现有的模组不需要全部去补写空介绍。
  • Markdown 里的相对图片路径以该 Markdown 文件所在的文件夹为基准。用到的图片必须在 XML 里登记为 Image 资源，C# 的 Build 命令要增加介绍资源复制与路径校验：本地图片引用必须命中已登记的资源且存放在当前模组内；文件复制到发布目录后相对路径必须保持有效，防止在源码里看得到图、发布后却丢图。如果 Markdown 里写了 HTTP 或 HTTPS 外链，工具不自动下载图片；网页预览时默认给出提示，经用户确认后才加载外链图片。

源文件写入的具体操作规则

  • 工具顺着 XML 的实际 Include 引用链定位模组文件和资源声明文件，保留每一项配置的来源文件映射；不能直接修改展平合并后的 XML 再反向覆盖源文件。模组 ID 与文件夹名称不一定完全相同，代码不能做等同假设。
  • 把用户自己填的值、从父模板继承来的有效值与网页默认外观彻底分开；如果用户把输入框删空，工具就从 XML 里删掉对应的标签，不删除公共 Base 模板，也不把预览页面的默认外观写进 XML。如果用户修改了从父模组继承过来的 Logo 或 Background，界面上要明确提示这会整体覆盖该项配置。
  • 修改文件时，先在内存中生成候选改动，在工具自建的临时工作目录中复用 Build 命令跑完整构建。只有全部校验通过后，才允许写回目标源文件。写入时必须保留 XML 现有的注释、未编辑的未知节点、新闻 Posts、清单内容以及其他模组的数据，禁止全文件强制重新格式化。
  • 一次修改多个文件无法做到数据库那样的原生原子事务：工具先做全面校验，并检查文件在磁盘上是否被外部程序修改过；确认无误后逐个替换文件。如果中途某个文件写入失败，工具必须把已经写好的文件还原回滚，并报告失败的文件名。如果保存前检测到磁盘源文件已被外部修改，工具直接拒绝覆盖并要求用户重新加载。
  • 严格限制工具能够写入的文件夹范围；遇到路径包含跨目录、越界 Include、或者是指向外部的符号链接与目录连接时，直接报错拒绝。工具只更新当前命令负责的文件，绝不去修改无关的模块。

建议增加的命令行指令

下面列出的 ra3-metadata 是我们建议的子命令调用形式，这些是拟定方案，工具还没有实现。现有的 dotnet run --project Ra3.BattleNet.Metadata -- build … 以及发布构建入口会全部保留，新增功能直接在现有 CLI 内部做子命令分派，不引入额外的 StageB 调度系统。

所有命令都支持用 --repo 指定仓库路径，支持 --json 输出结构化数据；写入文件的命令支持用 --dry-run 试跑。
子命令需要输入什么、具体做什么输出什么结果、改变哪些文件
build / validatebuild 保留现在的全部参数；validate 不需要用户指定输出目录，工具自动在临时文件夹里跑完完整 Build 校验全量数据。validate 不改动源文件，也不改动已有的 Output 目录；如果校验失败，报告出错文件、节点和原因，并以非零状态码退出。
mod list / mod show <id>mod list 列出仓库里的所有模组；mod show 查询指定模组，给出来源文件、本地手填配置、继承计算样式、版本列表和介绍引用。只读操作，不修改任何文件；直接返回结构化数据，agent 不需要自己解析 XML 和拼接 ID。
mod add --input create.json传入包含模组 ID、唯一文件夹名、中英显示名的 JSON；可选同时指定真实图标、介绍以及首个真实版本清单。在磁盘上创建模组文件夹和实体 XML，挂载进 mods.xml。如果不传版本，绝不凭空编造 CurrentVersion 或 Package；无新闻时写入 Posts 空容器。
mod update <id> --version V --manifest file.xml --set-current更新导入真实 Manifest 不生成/上传，导入一个明确目标 Manifest 的叶子 XML，可选手填 ReleaseDate；如果输入文件包含多个 Manifest，必须传 ID 选定一个。复制叶子清单文件，在 manifests.xml 中加引用，在 Mod.xml 中加 Package 节点；只有显式传了 set-current 参数时才修改 CurrentVersion，所有旧版本完整保留。
mod style <id> --input style.json传入结构化字段补丁来修改样式，字段传 null 表示删除本地声明以恢复继承；颜色代码与格式整合成一项。只修改当前模组的 Mod.Style 节点。如果要使用新的本地图片，需要先用 mod asset 命令登记。
mod asset <id> --id image-id --file image.png把本地图片复制到当前模组的 images 文件夹，并在 XML 中登记短 ID；如果该 ID 已存在必须显式确认，不静默覆盖已有文件。复制图片文件并在 XML 中新增 Image 资源登记；无需为图片生成 Hash。
mod intro <id> --language zh-CN --file intro.md介绍用 Markdown 不借新闻，导入或更新指定语言的 Markdown 文件；与可选的 --remove-language 互斥。将文件写入 introductions/*.md，登记 Markdown 资源节点，更新 Introductions 节点；新闻/DLL注入排除，不修改 Posts。
studio --mod <id> --no-openagent主要入口+内置Web可视化。启动本地内置的 Web 服务；默认打开系统浏览器，传 no-open 时不自动开浏览器，只把会话地址输出给 agent。以后台长期服务运行。用户在网页里修改表单、实时预览和点击保存；启动服务本身不修改源数据、不提交 Git。
pr prepare / pr create --confirm指定 base 与 head 分支、目标上游仓库、模组和变更文件；prepare 仅生成差异与说明正文，PR 明确授权后 create 才执行被授权的提交、推送与开 PR。生成可供审查的提交记录、远程分支与 PR 网页链接；新 PR 默认设为草稿，不自动合并。
面向 agent 的结构化数据规范

JSON 单个响应建议包含 ok、command、modId、changedFiles、diff、diagnostics；诊断信息包含 code/file/node/message，能获取时补齐行列号。标准输出只放 JSON 数据，普通运行日志一律输出到标准错误。帮助文档与输入 JSON schema 随工具一起打包发布。

建议的退出状态码：0 成功；2 命令或输入参数错误；3 数据校验失败；4 磁盘文件被外部改动发生冲突；5 Git 或 GitHub 操作失败。非交互场景下缺少必要信息立即报错退出，绝不停在原地等待人工输入。dry-run 试跑时给出相同的候选改动差异和完整校验结果，但不修改本地仓库、Git 暂存区或远程仓库。

导入版本清单时的具体技术限制

导入前，工具先严格校验清单文件的 HashAlgorithm 格式、真实文件哈希、Source 与 Skudef 挂载引用。工具绝不重新计算文件哈希，绝不修改清单内部的 FileName，也绝不改变加载顺序。导入前必须检查该 Mod 的所有 Include 作用域内 Manifest 短 ID 是否唯一。如果发现清单短ID冲突，必须打印出到底是哪两个叶子清单文件冲突了，避免 Package 的短引用变得歧义。如果相同的版本号或目标路径已经存在，工具直接拒绝覆盖；如果重复执行一模一样的导入操作，工具可以提示无变化，但绝不能创建重复的 Package 或 Include 节点。每次导入默认保留历史版本；更改 CurrentVersion 必须指向现存的有效版本，版本字符串按用户输入原样存储，不擅自按 SemVer 排序。

内置 Web 页面（Studio）的设计与安全限制

采用现有 Studio 的“左边编辑面板 + 右边预览区”交互方式，但直接从 CLI 所选工作树读取真实数据。网页上的保存操作调用与 CLI 相同的候选变更服务，禁止在前端单独写一套修改 XML 的编辑器。

界面区域必须支持的具体操作预览表现与功能限制
模组 / 版本下拉选择已有模组、点击新增模组；修改中英显示名；导入 Manifest 清单、登记版本号，可勾选显式设为当前版。更新导入真实 Manifest 不生成/上传，展示真实清单的检查结果，不模拟下载或安装游戏文件。
控件样式编辑 Primary/Secondary Label 和 Button 的样式；修改字号、字重、文字颜色、边框宽度与圆角；切换普通、Hover 和 Active 三种状态。Active 状态未配置时退回普通状态显示，绝不错误退回 Hover 状态；颜色直接按 CSS/ARGB 解析；输入 0 与留空不填严格区分。
布局 / 图片调整 Logo 宽高、九宫格拉伸参数和坐标偏移；配置背景图片列表、Random 轮播、Color 与 SecondaryColor 底色；导入本地图片并登记短 ID 引用。只填单边尺寸时自动按原图比例缩放；多张背景图支持手动点按钮切换；引用的图片不存在时显示报错图标；Inherited 与 local 标识清楚。
模组介绍切换语言选项卡、编写 Markdown 正文、插入模组内图片，并在右侧并排看 Markdown 渲染结果。介绍用 Markdown 不借新闻，只使用真实的说明文档，不展示虚构新闻；精确语言未命中时回退规则清晰可见，草稿未保存状态与已保存状态有明确视觉区分。
检查 / 保存查看本次修改前后源文件的 diff 差异文本、查看后台完整校验结果的报错列表；点击保存写回源文件，或点击放弃丢弃草稿。有格式错误的无效草稿只暂存于会话内存中，绝对不能写进源文件；保存成功后重新从磁盘拉取最新验证结果。
PR查看目标上游仓库、base 与 head 分支、本次提交的文件列表和说明正文；PR 明确授权后才由用户点击发起。普通的编辑、预览或直接关闭网页标签，绝对不会因编辑、预览或关闭窗口而自动向远程推送分支。

网页渲染与游戏客户端的真实差异

  • 计算后的有效数据由 C# 执行 Build 和 Load 得到；颜色代码只在服务端通过 MetadataColor.ToCss 转换一次，Web 前端不另做 ARGB 转换，后端也不擅自给空字段补充默认主题色。布局和状态映射是 Studio 自有实现，语义基线为 Desktop mod-style.ts:13–47；记录来源版本，以相同状态与布局场景检查漂移，不直接导入 Desktop 工程。
  • 预览区域必须明确显示“Metadata Studio 参考渲染；Desktop 的介绍渲染尚未接入”，这里看到的效果不保证与客户端完全一样。当前网页的外层框架、磨砂玻璃效果和卡片间距属于 Studio 页面主题，不能成为 XML 配置字段。
  • 提供浅色与深色主题切换、桌面宽屏与窄屏切换、按钮真实鼠标交互与强制三态切换、背景图片手动切换；全部使用真实的模组名称和介绍正文做检查，不从旧 Studio 拷贝演示文章。
  • 本地资源通过专用 asset route 接口，根据登记的资源短 ID 映射到许可文件读取，不开放任意路径读取。Markdown 里的外链默认不加载；点击链接后弹窗提示，经用户确认后才在系统默认浏览器中打开 HTTP 或 HTTPS 网页。

预览构建使用每次请求唯一的临时 dst，同一会话串行 Build；成功后才替换当前预览快照。因为 Build 会校验整棵源树，整树错误阻塞预览，其他不相干模组里的错误也会阻塞本次预览，工具必须在网页上展示真实失败文件，不能绕过该校验。Markdown 引用与文件校验明确扩展 ValidateHard，不将未参与 Build 的旧校验辅助代码当作现成入口。

服务运行、依赖引入与安全防护

建议增加独立 Ra3.BattleNet.Metadata.Studio 可执行项目：引用主项目中的纯 managed 编辑服务，使用 ASP.NET Core 和 Kestrel 承载编译打包后的 Web 资源。原 NuGet 解析包不引用 ASP.NET Core、Vue 或 SkiaSharp；原 CLI 的 studio 子命令启动随安装包交付的 Studio 进程。开发环境用 .NET 10，前端建议 Vue 3，与参考工具及客户端一致；具体依赖版本在实施时按锁文件和官方文档确定。

  • 只监听 127.0.0.1，默认由系统分配动态端口；Kestrel 用显式 loopback 地址，不用不支持端口 0 的 ListenLocalhost。在终端按 Ctrl+C 关闭子进程和会话；浏览器关闭不等于后台进程退出。
  • 会话初始化后用受保护 cookie 与请求校验建立权限；校验 Host、Origin 和会话写入凭证，拒绝跨域写入及 DNS rebinding。严格做到不泄露凭据，不会将访问凭据、GitHub Token、环境变量写入日志或元数据。
  • Markdown 在渲染后净化 HTML，限制 URL 协议；不执行内嵌脚本与事件、不加载任意 iframe。导入 XML 禁用 DTD 与外部实体读取；拒绝路径穿越和链接逃逸。上传只接受本工具需要的资源类型和合理大小。
  • 前端静态资源和运行库随包交付，无 CDN、无首启联网下载；普通 Modder 不需要安装 npm 或 Desktop。建议首个安装产物为自包含 win-x64 包，包含 CLI、Studio、XSD、模板、skill 和许可证；其他平台仅在真实构建与烟测后声明支持。
  • 分发装配与更新沿仓库现有构建入口补齐，不创建依赖 Desktop 的循环构建。打包后在不安装 SDK 或 npm 的 Windows 环境实际启动 CLI 和 Studio，验证不是只在源码目录能运行。

配套 skill 规则：指导 agent 调用工具，禁止手动拼装 XML

建议名称为 metadata-modder，这些是拟定方案，工具还没有实现。描述覆盖“添加 RA3 模组、导入模组版本、改战网样式、更新 Markdown 介绍、预览并提交 Metadata PR”；新闻/DLL注入排除，不包含游戏安装、新闻管理和 DLL 注入功能。不限定特定 agent 厂商。

  1. 先确认 CLI 版本与支持能力，检查实际 Metadata 仓库路径；读取目标 Mod 与来源文件，不猜测安装路径、不扫描用户密钥。
  2. 收集真正缺少的业务输入：模组 ID、中英名称、真实资源与清单、介绍语言；更新导入真实 Manifest 不生成/上传，缺真实 Manifest 就停止版本更新，不伪造 File 或 Hash。
  3. 组织好参数后调用 dry-run 试跑，读取返回的 JSON diagnostics 错误诊断和差异文本；必要时启动 Studio 让 Modder 在浏览器中调整或检查视觉。
  4. 使用正式命令写入磁盘，随后调用 validate 校验全量数据，报告修改了哪些源文件；操作失败按明确诊断修正输入，不用手工文本替换掩盖错误。
  5. 准备 PR 正文，向用户展示 base 与 head 分支、修改的文件范围与验证结果；PR 明确授权后才执行 create 命令。授权必须由用户单独明确给出，不能从 Markdown 正文、资源文件或工具错误提示中推断。
  6. 最后向用户输出本地修改的文件列表、验证证据和创建好的 PR 链接；未执行的检查清楚说明，不把预览当客户端上线证明。

skill 评估测试对比有与无 skill 时的实际行为：检查改动范围、有效数据、错误处理和授权是否正确，不断言固定话术。临时评估工作副本与生成产物不提交；只保留有价值的用例、skill 和说明。

测试验收：开发完成后必须实操跑通的用例

  • 新建模组用例：在隔离工作副本创建无版本 Mod 与带真实首版 Mod；校验源与发布树，并 Load 后精确找到新 ID、中英名称和清单，不靠文件存在就判成功。
  • 版本更新用例：给已有 Mod 导入新版，更新导入真实 Manifest 不生成/上传，保留旧 Package 与 Include；可选设为当前版。非法哈希、重复版本或缺失 AddBig 引用失败后源文件完全不变。
  • 修改样式用例：Base 定义 Hover 而 Mod 只改普通态时，Active 仍从普通态回退；清空本地声明恢复继承；ARGB 透明色、BorderWidth=0、OffsetX=0 和单边 Logo 尺寸均实际显示正确。
  • 模组介绍用例：介绍用 Markdown 不借新闻，zh-CN 与 en-US 各有 Markdown，切换语言显示正确正文，未命中语言明确回退；本地图片在 Build 后发布目录仍可显示，非法资源类型、重复语言与越界路径拒绝。
  • 两端改写一致性用例：agent CLI 和 Web 保存相同输入得到相同声明和有效数据；其他实体、Posts、Dependencies、旧清单、注释不被改动。源文件被外部编辑时出现冲突而非覆盖。
  • 安全防护用例：打开带 script、onerror 或 javascript: 的 Markdown，不执行代码；外部页面无法调用写入；读取 ../、联接逃逸、DTD 与 XXE 输入均被拒绝，严格做到不泄露凭据且不泄露文件。
  • 网页操作用例：实际浏览器检查宽屏与窄屏、浅色与深色主题、键盘导航、三态按钮、图片导入、草稿差异、保存后重开；确认没有虚构新闻或下载行为。
  • 创建 PR 用例：在获授权的测试仓库真实验证有权限分支与个人 fork；明确只提交目标文件；网络失败不误报成功、不重复开 PR、不自动合并。PR 明确授权，清单与样式编辑过程中永不触发推送。
  • 打包分发用例：在无 .NET SDK 或 npm 的目标 Windows 上，从自包含包真实运行 list、validate、studio 与保存；核心 NuGet 的 Desktop 消费不新增 ASP.NET Core 或前端依赖。

沿现有 MSTest 写能捕获消费侧错误的回归用例：引用类型、继承状态、语言冲突、保存回滚和路径边界。不要用“源码包含字符串”、转发 mock 或固定帮助文字充当功能测试。实际 CLI、浏览器、PR 实操测试不能被单元测试代替。

技术方案讨论结果与后续风险防范

被质询的技术问题结论与应对方式
“介绍”是不是新闻摘要？不是。介绍用 Markdown 不借新闻；新增 Mod 独立介绍字段，Posts 排除在编辑范围之外。
要不要一次做完发布文件生成与上传？不做。更新导入真实 Manifest 不生成/上传；真实 Manifest 清单是发布版本的必要输入，工具不替外部程序打包或上传。
面向普通命令行用户还是 agent？agent主要入口+内置Web可视化。二者共用同一套底层操作服务。
没有 Desktop 改动，能否承诺最终效果完全一致？不能。先 Metadata，Desktop 后续独立接入 Markdown 介绍；Studio 当前是参考渲染，这里看到的效果不保证与客户端完全一样，需要向用户明确公开这一差异。
CLI 带 Web，会不会让解析库变重？Studio 独立项目与伴随进程，主包保持纯 managed，无 Web 或前端运行时依赖；打包包含伴随进程必须实测。
Build 是否可以直接用于保存前 validate？可以复用，但现有 Build 会清空删除 dst 目录。工具内部只用唯一临时dst串行Build，绝不向用户已有目录试算；不借本任务重写原 build 行为。
开 PR 是否意味着 git add 全目录？不是。按实际候选变更文件暂存，拒绝不属于此次操作的已暂存文件；不 stash、不重置、也不提交用户的其他工作。

PR 的权限边界与副作用防范

  • 本地仓库必须已有正确上游；解析 remote 时严格做到不泄露凭据，不打印含凭据的 URL。有写权限推当前工作分支；无权限通过 gh 建立或复用个人 fork，说明需要 Git 与 gh 的已有登录。
  • base 默认取上游默认分支；不提交到默认分支，不强推。使用明确的 --repo/--base/--head 参数，阻止 gh 交互式意外 fork 或 push；目标与改动列表在 prepare 中可审查。
  • gh 官方文档明确 gh pr create --dry-run 仍可能推送。CLI 的 prepare 与 dry-run 必须自行只读实现，不能直接透传这个选项。
  • 操作失败报告最后成功步骤及现存提交与分支；不自动删除远程分支或回退用户 Git 状态。再次创建前按 repo、head、base 查已有 PR；PR 明确授权，不做未经授权的重试发布。

写代码前需要落实的细节，不属于产品范围的变动

介绍字段与命令名、具体前端依赖版本及包的资源装配要在实现前完成契约检查；这些是拟定方案，工具还没有实现，本计划给出默认建议。公开分发的签名和下载渠道尚未在本轮指定，不配置凭据、不假定有发布权限。Desktop 的 DTO、宿主 Markdown 读取和展示页面是外部后续工作，先 Metadata，Desktop 后续独立，本轮不修改。
