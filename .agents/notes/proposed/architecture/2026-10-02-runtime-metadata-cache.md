# Agent Note: Metadata 解析库的运行期本地缓存

Status: proposed

## Problem

目前现有的 [MetadataBuilder.cs](../../../../Ra3.BattleNet.Metadata/MetadataBuilder.cs#L169-L209) 代码，每次通过 HTTP 网页链接加载数据时，都会新建一个 HttpClient，把拉回来的文本随手写到一个临时文件里，解析完后转头就把它给删了；这根本不是一个能真正持久保存数据的本地缓存。这就导致桌面客户端每次重启，都必须重新联网去服务器拉取总清单和各个版本的独立清单。一旦遇到网络不好或者服务器偶尔卡顿，界面上的 Mod 列表直接展示不出来；断网更不应该导致本机原本已经装好的游戏版本直接消失。

这套本地缓存逻辑理应由 Metadata 解析库自己封装提供，而不是让 Desktop 桌面端在 App 和 Mod 两个不同的读取器里各自重复写一遍轮子。桌面端主程序只负责指定缓存存到哪个目录、传入日志接口、设置超时时间和决定什么时候调用；而解析库本身绝不写死 `RA3BattleNetData` 这种具体路径、绝不负责下载几个 G 的大体积游戏安装包，也绝不插手管理本机到底装了哪些版本。

本仓库此前尚未建立架构决策笔记目录，因此新建本篇作为 M1 提案。整套系统的全局要求见 [下载与安装总体指导](../../../../../Desktop/.agents/notes/proposed/architecture/2026-10-02-download-system-guidance.md)；本地已安装记录的格式规范见 [M2](../../../../../Desktop/.agents/notes/proposed/architecture/2026-10-02-local-installation-metadata.md)。

## Proposal

### 1. 缓存的数据边界与分工

解析库缓存的数据分为以下四类：

| 数据类型 | 如何向服务器刷新 | 刷新失败时的兜底表现 |
|---|---|---|
| 根清单总表（metadata.xml） | 客户端每次启动时，发送一次带超时限制的有条件 HTTP 请求 | 继续使用本地最后一次有效的快照；如果初次安装完全没有缓存，返回不可用（Unavailable） |
| 各版本的独立文件清单 | 优先拉取当前版本或用户刚刚选中的版本，其他未选中的版本在后台低优先级预取 | 对应的版本包标记为资源未就绪，绝对不拿空数据去发糊涂请求 |
| 界面图片与 Markdown 公告 | 根据界面展示的需要动态拉取，做好排重与并发限额，支持低优先级后台预取 | 图片显示占位空白、更新说明提示暂不可用，但绝对不阻塞本地已安装版本的正常游玩 |
| Updater 增量更新清单 | 只有当用户触发了更新任务后，才按照固定的版本标识去拉取 | 如果校验失败，绝不自动开启整包安装 |

需要特别强调：清单里引用的几个 G 的大型游戏压缩包，绝对不属于元数据缓存的管辖范围。大体积文件的断点续传全部归下载模块掌管；元数据缓存层绝不能因为在 XML 里解析出了某个下载链接，就自作聪明去递归下载它。Markdown 文档里包含的各种外部网页超链接，也坚决不纳入自动抓取范围。

### 2. 拟议的核心服务接口

```csharp
Task<CatalogLoadResult> OpenAsync(CacheOptions options, CancellationToken token);
Task<CatalogRefreshResult> RefreshAsync(CacheOptions options, CancellationToken token);
Task<CachedResource> ResolveResourceAsync(
    SnapshotLease snapshot, ResourceRef resource, CancellationToken token);
```

输入参数：入口 URL、主程序指定的本地绝对路径 `CacheRoot`、支持依赖注入的 HttpClient、网络超时时间与最大并发配额，以及日志记录接口。代码绝不能静默篡改操作系统的全局网络代理设置或证书安全策略。

输出结果：快照 ID（SnapshotId）、根清单原始文本哈希、数据来源 URL、获取时间戳、数据修订版本、状态枚举（最新 / 已过时但可用 / 完全不可用）、各项资源的就绪状态、本地只读文件路径与只读流，以及安全租约。

- `OpenAsync` 只负责快速打开本地已经校验过的历史快照，在必要时恢复缓存指针，绝不在后台无限期卡死等待网络；
- 桌面端启动时的规矩：先调用 `OpenAsync` 秒开本地已有数据，然后再单独发起一次 `RefreshAsync` 异步联网刷新。如果是初次安装完全没有本地缓存，可以给一个有超时限制的等待窗口；但无论如何绝不能阻塞本地已安装游戏列表的加载；
- 同一个进程访问同一个服务地址，共享同一个刷新任务，主程序、Mod 模块和更新检查点绝不能各自重复向服务器拉取根清单；
- 跨进程时，通过文件互斥锁保护当前的缓存指针；下载资源支持并发拉取，但针对同一个资源文件会自动合并成单次请求；
- 老代码里现存的 `MetadataBuilder.Load(pathOrUrl)` 继续保留向下兼容；新引入的缓存 API 绝不破坏原有的同步加载语义，也绝不反向引入对桌面端的任何依赖。

### 3. 本地磁盘目录规划与文件身份

桌面端主程序把缓存根目录指定为 `RA3BattleNetData/Metadata/Remote`。解析库在内部按以下结构组织：

```text
current.xml                                          # 指向当前生效的快照
current.xml.pending                                  # 准备写入的临时指针
current.xml.previous                                 # 上一份生效的历史指针
snapshots/<root-digest>/metadata.xml                 # 历史根清单原文
snapshots/<root-digest>/resources.xml                # 资源引用映射表
objects/<sha256-of-resource-bytes>/payload           # 按内容哈希存放的具体资源实体
requests/<safe-request-key>.xml                      # 请求上下文记录
staging/<attempt-id>/...                             # 下载解压的临时中转目录
```

- 一个 `CacheRoot` 目录必须牢牢绑定一个规范化的原始入口地址（OriginEntryUri）和请求配置，在初次写入时记录在 `origin.xml` 里；后续如果请求入口或认证范围对不上，坚决拒绝复用该目录，主程序必须另选子文件夹。绝对不能因为两个不同网址返回的根 XML 刚好一样就混用资源映射，因为相对路径的解析严重依赖服务器根网址；
- 根清单和具体的资源对象，在保存时必须完整保留服务器返回的原始 XML 和图片字节，绝不为了适配本地路径而随手篡改原文；原始文本的哈希摘要必须保持稳定；
- SnapshotId 由根清单原始文本的 SHA-256 哈希计算得出；清单里的 `ContentRevision` 仅作为发布者贴的版本标签，不能单凭它来证明文件绝对一致；
- HTTP 缓存验证必须绑定完整的请求身份（包括初始入口、经历跳转后的最终 URL 以及内容协商参数）；ETag 绝不是跨不同镜像源通用的标识；
- 下载地址里包含的时效敏感 Token 参数，坚决不打进普通日志和可读索引中；必须的敏感数据走安全的私有存储，界面上展示的必须是脱敏后的干净地址；
- `resources.xml` 负责记录资源的注册 ID、服务器 URL、预期哈希与大小、本地对象摘要、就绪状态以及最近的报错信息；这些小文件的保存同样采用防断电崩溃的安全写入机制；
- 存入 `objects/` 目录的对象文件绝对不可就地修改。遇到内容完全一样的资源可以直接复用已有文件读取，绝不能把一个文件直接覆盖修改成另一个资源；也绝不搞不可控的硬链接共享。

### 4. 有条件的增量刷新算法

1. 拿到刷新锁，读取当前生效的 `current.xml` 指针以及对应的根清单；
2. 发起带条件的 HTTP GET 请求：只有在本地文件真实存在且校验通过时，才带上 ETag 和 Last-Modified 头；要是本地文件其实丢了，绝不能光凭服务器回一个 304 就假装成功；
3. **如果服务器回了 `304 Not Modified`**：说明服务器端没有变动，确认本地根清单完好无损即可；如果发现本地文件坏了或缺了，立刻无条件重新发起全量拉取；
4. **如果服务器回了 `200 OK`**：采用流式写入临时候选文件，严格限制文件最大长度；严密拦截防盗链的 HTML 网页、畸形 XML、外部实体（XXE 防御）以及非法根节点；
5. 使用 XSD 模式和必要的业务规则，严格验证根节点、实体 ID 和资源引用；坚决不把未知字段当成正常兼容；
6. 把校验通过的候选文件保存为新快照；优先拉取当前用户正在查看的 Mod 或应用所需的资源。允许目录处于“根总表有效、部分附属资源正在下载”的中间快照，但必须逐项准确向界面汇报哪些文件已就绪；
7. 切换当前指针时，严格走 pending -> current -> previous 的原子安全切换流程；遇到中途断电崩溃，下次启动时自动挑选版本号最高的那一份；
8. 后台继续拉取其他登记的资源；任何资源下载完成，只能写入当前快照对应的映射表里，绝对不能串到别的快照中；
9. 刷新一旦遇到网络失败，完整保留上一份旧快照和报错时间戳。向调用方返回 Stale（已过时但可用），并让界面给用户显示“当前正使用离线缓存”，坚决不把空目录当成正常的刷新结果。

建议的默认参数：拉取根清单总超时 15 秒、启动时自动重试最多 2 次并带退避等待，资源下载并发数限制为 4；根 XML 文件体积上限 8 MiB、独立清单上限 32 MiB、单张图片等媒体资源上限 32 MiB。这些限制不能等到下载完才去查，而是在流式读取过程中实时把关。

### 5. 根总表与独立子清单的一致性保障

根总表能够顺利打开，并不代表它下面引用的所有子清单都在服务器上发布完整了：

- 凡是在清单里写明了预期哈希和文件大小的资源，下回来之后必须严格核对，坏文件绝对不能放进当前快照中；
- 最理想的发布规范是：在大总表里直接写明各个独立子清单原始文本的 SHA-256 哈希，或者使用带哈希防覆盖的不可变资源下载链接；
- 如果历史老清单里只写了 URL 没给强哈希，那只能证明下回来的文件格式没错，没办法证明服务器跨多个文件发布时绝对处于同一时间点。界面展示可以向下兼容，但内部要打上 `LegacyBinding`（历史老绑定）标记；
- 客户端的自动整包安装，必须能够严格验证目标版本与下载包的绑定关系；一旦缺少明确凭证，立刻报错为 `InsufficientManifestBinding`，坚决不靠“碰巧多拉了一次总表”来糊弄；
- Mod 的老清单在用户点击选中时，将实际取得的合法文件原文和参数锁死，存入本地安装记录中；哪怕服务器后来把同版本号的内容给换了，也绝对不影响正在跑的任务；
- 如果服务器刚推了大总表、但子清单文件还在排队上传中：客户端对该版本标记为等待或报错，坚决不拿别的老版本文件或者上次存的旧数据来冒充新清单。电脑里原本已装好的旧版本则丝毫不受影响，正常可玩。

### 6. 资源网络地址与本地路径解析

现有的 [MetadataResourceUri.cs](../../../../Ra3.BattleNet.Metadata/MetadataResourceUri.cs) 在面对本地根目录时会生成 `file://` 协议链接。因此新的缓存 API 必须牢牢记住 **OriginBaseUri**（服务器原本的基准网址），所有相对路径（Source）必须先按照服务器的原本网络网址去拼装解析，然后再去本地缓存库里按哈希找对象，绝对不能直接拿本地的缓存文件夹路径去当相对路径的基准。

解析方法 `CachedResource` 会给调用方返回本地只读文件路径和真实的来源信息。上层业务代码**绝对不允许自己在外面手动拼 `cacheRoot + remoteSource`**，否则极易踩进 `../` 跨目录逃逸、大小写冲突、非法盘符以及覆盖别人文件的各种大坑。

下载源支持显式配置的 HTTP 或 HTTPS 链接；`file://` 协议仅供开发者在本地调试开发时使用，坚决不接受远端清单指向用户电脑上的任意本地文件。重定向要严格限制跳转次数和跳转协议，跨域名跳转时绝不泄漏认证头，坚决不放过任何证书安全错误。

界面展示用的图片外链同样必须通过这套资源解析器来读，避免总表明明已经缓存好了、界面展示时还每次去直连外网图片。历史老版本的图片可以延迟按需加载，老版本的子清单文件低优先级慢慢预取，没必要一启动就把全网所有历史文件全部拖下来。

### 7. 离线支持、本地已装版本与文件租约

- 本机安装游戏所必需的启动清单，全部保存在本地的 Installed 专属记录里，根本不需要指望远端缓存永久不坏；
- 本地记录里彻底不存任何界面排版和样式；界面展示时尽量去关联当前或历史的远端缓存，要是缓存真的被清空了，直接显示占位文本即可；
- 安装或下载任务在把必要的配置参数和清单快照存入自己的专属目录后，就可以释放掉大部分缓存租约；如果仍然需要引用缓存对象，必须持有明确的租约；
- 缓存清理机制只清理那些既不在 current/previous 列表中、也没有任何读者租约或活动任务引用的孤儿文件；清理前先做标记再安全回收，绝不能因为服务器把某个版本下架了，就自作主张把用户本地装好的游戏也给卸载了；
- 默认保留一份当前生效快照、一份上一版本备份，以及带有活跃租约的对象；当硬盘空间达到配额上限时，优先清理没有被引用的旧图片。如果磁盘空间实在紧张，保留好当前唯一的有效根清单并弹窗报错，绝对不为了腾地方先把唯一能用的缓存给删了；
- 缓存刷新或者清理报错，绝对不能篡改本地已安装记录，绝对不能影响下载队列的最终状态，也绝对不碰 Updater 的更新基线。

### 8. 代码结构与分阶段开发步骤

建议在 Metadata 项目内部新增 Cache 子目录，添加 CacheOptions、MetadataCache、CatalogSnapshot、ResourceResolver、CacheStore 等强类型类；保持纯 C# 托管实现，不引入任何特定的 UI 库或安装器依赖。

1. 第一步：定义好结果模型、错误码，支持注入式 HTTP 客户端、虚拟存储和模拟时钟；编写完备的纯离线单元测试；
2. 第二步：实现根清单的 current/pending/previous 安全写入协议，以及带超时的有条件增量刷新；
3. 第三步：实现保留服务器原本 Origin 基准网址的资源解析器，以及基于内容哈希的对象缓存库；
4. 第四步：实现资源哈希强校验、快照引用租约，以及多级预取优先级调度；
5. 第五步：桌面端统一由 `AppMetadataReader` 和 `ModCatalogSource` 接入这套缓存；进程内坚决不留多套各自为政的根总表。
   【当前落地现状】这两条业务线已经顺利接到了缓存层（`MetadataRuntime`，缓存根目录指定为 `RA3BattleNetData/Metadata/Remote`）：
   启动时先打开本地快照，后台异步刷新，各个版本的叶子清单每次都向服务器核验。
   **更新检查点（Update endpoint）暂时不去接管它** —— 它负责的是日常增量更新那条线，本轮明确不动它，
   因此“一个进程只持有一份根总表”目前在 App 和 Mod 这两条线上已经完全成立。
6. 第六步：发布端逐步给独立子清单补上 SHA-256 强哈希和防覆盖链接；先发布具备向下兼容能力的新客户端，随后再推新版数据架构。

## Alternatives considered

- **每个桌面端读取类各自管各自的缓存**：虽然改动局部简单，但会导致同一个程序频繁重复联网、两边缓存数据打架、路径安全规则各写各的；坚持由解析库提供通用的标准缓存服务，桌面端只管调用和生命周期。
- **每次都把根清单下载到一个固定名字的文件里直接覆盖**：看似最好理解，但只要下载中途突然断网或者程序闪退，本地唯一能用的一份目录直接就被撕裂损坏了；坚持使用不可变对象和三文件安全指针切换机制。
- **启动时把清单里引用的所有几个 G 的大型安装包全部下载下来做本地镜像**：离线体验虽然拉满，但只要启动就会把用户的网速和磁盘彻底占满；缓存层必须恪守本分，只负责拉取控制清单和轻量展示资源，大文件的下载必须作为用户明确发起的独立任务。
- **把界面展示样式直接抄一份写进本地安装记录 XML 里**：离线展示虽然省事，但这严重违背了用户明确拍板的“本地安装记录必须去样式”的原则，而且极易产生过期不更新的脏样式；展示缓存与本地安装事实必须彻底分家。

## Acceptance criteria

- MC-01：首次拉取根清单成功返回 200 后，下次启动能正常带上验证头，服务器回 304 时直接复用本地缓存；如果本地对象损坏或丢失，回 304 时必须能强制发起一次无条件全量重新拉取，绝不虚报成功。
- MC-02：面对断网、网络超时、服务器返回防盗链 HTML、XML 提前截断以及格式错误等异常情况，本地最后一次有效的快照丝毫不受破坏。
- MC-03：服务器更新了根总表，但某个版本的子清单还没传完或者哈希对不上时，该版本明确提示不可新装，但电脑里原本已经装好的老版本照样能正常启动玩。
- MC-04：本地缓存里的相对资源依然严格按照服务器原本的基准网址解析，任何试图跨域名越界访问或者跳脱出根目录的恶意路径全部被拦截；两个不同的入口如果返回了相同的总表但相对资源不同，坚决不共用同一个 CacheRoot 映射。
- MC-05：App 和 Mod 两个模块在启动时同时发起请求，内部自动合并为单次网络刷新；取消其中一个调用者，绝对不破坏另一个调用者的有效租约。
- MC-06：图片等媒体文件下载失败时只显示占位图；初次完全断网启动（返回 Unavailable）与连上服务器但服务器上啥都没有（空目录），在状态枚举上有明确区分，方便界面对症提示。
- MC-07：在快照指针切换和垃圾清理的每一个崩溃断电点，系统重启后都能自愈并保留一份有效的目录，正在被引用的活动文件绝不被误删。
- MC-08：元数据缓存刷新流程从头到尾绝对不触发任何几个 G 的大体积游戏安装包下载，也绝对不去动用户的本地已安装记录。

## Risks

- 历史老版本由于当时没有记录子清单的 SHA-256 强哈希，这是客观的历史事实，在代码数据模型里必须如实表达出来，绝不能拿本地自己算出来的 SHA-256 去自欺欺人假装是发布者当初签署的预期值。
- 如果无脑在后台把所有图片全拉下来，会浪费用户的网络流量并占满磁盘；因此默认采用按需拉取和低优先级预取策略，总表加载成功与图片是否全部就绪不能捆绑在一起当同一个指标。
- 缓存根目录保持同形，不代表所有业务代码都能自觉用对相对路径解析方法，必须严格收拢到统一的入口类上，坚决杜绝在外面自己随便拼 URL 的行为。
- 本方案不强求立刻去改动线上现有的发布数据；在缺少强哈希绑定的兼容过渡期内，应当停用对应的自动安装整包逻辑，而不是悄悄把安全防御标准给放宽。
