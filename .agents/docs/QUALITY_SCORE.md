# 质量评分

按领域打分，1 最差、5 最好。分数低不丢人，藏起来才丢人；每季度过一遍，变化写进提交信息。

| 领域 | 分数 | 依据 | 短板 |
|---|---|---|---|
| 数据契约 | 5 | 源模式与发布模式各一份 XSD；构建器硬失败，任何断链都产出不了 | 字段说明靠手写文档，尚未从 XSD 生成 |
| 构建流水线 | 4 | 七个阶段顺序固定，失败清空输出；资源拷贝与独立清单再展平都有测试 | `MetadataBuilder.cs` 775 行，`Build` 与 `ValidateHard` 挤在同一个类 |
| 解析库查询 | 5 | 延迟枚举 + `Catalog` 快查；空值、缺失版本都有明确异常或 `null` 约定 | 无语义版本范围，`Version` 只做精确提示 |
| 磁盘缓存 | 3 | 路径映射是纯函数，地址归属、ETag、暂存文件都有测试 | `MetadataClient.cs` 约 1700 行，单类承担刷新、预加载、图片三条流程 |
| 测试 | 4 | 24 个测试文件覆盖构建、模型、缓存、兼容性；MSTest 单一框架 | 没有覆盖率统计，没有预加载耗时基准 |
| 文档 | 4 | `AGENTS.md` 只当地图；专题事实源按任务拆分；生成物与链接由脚本守 | 属性表与 XSD 双写，靠人工同步 |
| CI | 3 | 部署流水线跑真实构建，提交标识写进产物 | 此前只有部署流程；本次加了 PR 校验（测试 + 构建 + 文档） |
| 发布 | 4 | EdgeOne 自动部署；Cloudflare 走 `npm run deploy` | 两条线的构建参数靠人工保持一致 |

## 打分口径

- **5**：有机器守卫，坏了会立刻报错。
- **4**：有测试或流程，但依赖人记得跑。
- **3**：能用，有明确已知风险，改动时容易踩。
- **2**：主要靠口头约定。
- **1**：没人知道现在是什么状态。
