# 工程信条

短清单。违反其中任何一条，改动就别合。

## 1. 仓库是唯一事实源

Agent 在运行时看不到群聊、在线文档和口头的约定。凡是会影响数据格式、客户端行为、构建流程的结论，必须写进仓库里的 Markdown、XSD 或测试。写不进仓库的共识，等于不存在。

## 2. 能机器检查的规则，不靠自觉

- 数据格式由 XSD 与构建器校验，不写“请注意不要写错”。
- 笔记结构、生成物新鲜度、文档链接由 `scripts/verify-docs.mjs` 拦截。
- 构建器的报错必须能直接看出改哪个文件的哪一行；报错里带修复动作，而不是只给失败现象。

## 3. 失败就停，不产出半成品

构建器任何一步失败都清空 `Output/` 再抛错，命令行返回非 0。不吞异常，不加“先让它过”的兜底分支，不写掩盖源头的补丁。

## 4. 边界集中，内部自由

- ID 前缀、资源路径、缓存布局、语言比较这类跨模块约定，只在一处实现，其他代码调用它。
- 具体实现方式（换行风格、私有方法拆法）不设规矩，diff 能看懂就行。

## 5. 发布契约优先于实现便利

`SchemaVersion` 是给客户端的承诺。改样式、加可选字段、改默认值都不提升版本；只有旧客户端确实无法继续工作才提升，并且要同时安排客户端升级路径。

数据作者写起来顺手，不能以让客户端猜路径、猜格式为代价。

## 6. 说人话

- 文档、报错、提交信息用中文说清“做了什么、为什么、影响谁”。
- 不用“根”“落地”“打通”“赋能”这类词；确切含义查 [glossary.md](glossary.md)。
- 需求不清楚就问，范围拿不准就问，不靠猜扩大改动范围。

## 7. 非平凡改动留下决策

代码能说明“怎么做的”，说明不了“为什么不那样做”。改行为、改契约、改流程必须写笔记，备选方案要写真实考虑过的，不是为了凑格式。
